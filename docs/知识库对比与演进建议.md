# 梯见知识库、WeKnora 与 Graphify 的区别

核查日期：2026-09-17。梯见依据本地 0.7.0 源码；外部项目依据公开仓库、README、配置和部分源码。WeKnora 核查 main 提交 `5574ebc0118e862ee1519d3700b8e73eb5b13c5b`；Graphify 核查默认 v8 分支提交 `26b02b5e3430e4ab85dd7e72c7b98836d8e65c48`（其 main 分支是旧版本，不能混用功能和许可说明）。本次没有部署这两个服务，也没有进行同一文档集上的质量、速度或成本对测。项目自报的基准数字不等于我们的使用效果。

## 先明确要解决的问题

知识库至少包含三个不同工作：保存可追溯的资料，检索回答问题所需的证据，管理知识之间的关系与更新。梯见目前更关注“资料如何进入研究和创作，以及哪些结论经过用户确认”。WeKnora 更完整地覆盖文档理解与检索问答。Graphify 更关注把混合文件中的概念和联系组织成可查询的图。

因此，不建议直接用其中一个替换整个工作台。对我们最有价值的路线是保留业务流程，再补强检索能力；关系图谱根据具体需要引入。

## 对比

| 维度 | 梯见当前实现 | WeKnora | Graphify |
|---|---|---|---|
| 核心用途 | 行业资料、对标、定位、写作、核查与知识确认连成工作流程 | 文档知识平台，检索问答、Agent 和 Wiki | 将代码、文档、图片等组织为关系图，查询联系与路径 |
| 获取证据 | 手选来源＋关键词匹配已确认知识；整段正文有限截取 | 文档分块、向量与关键词检索、重排及图相关能力 | 代码 AST 和语义提取；遍历概念及关系 |
| 长文与大量资料 | 较弱：没有独立的分块向量索引，容易遗漏不同表达或截断后的证据 | 更适合建设专门的文档检索服务 | 适合关系导航，不能把图中关系直接当作完整原文证据 |
| 知识治理 | 候选确认、来源、适用时间/地区、冲突记录、身份偏好分离 | 文档/片段修订、知识库与工作区权限、Wiki 与记忆等 | 关系来源和推断标记有参考价值；需要接入我们的用户确认流程 |
| 对内容运营的贴合 | 较强：已有公众号、对标、身份、稿件和复盘流程 | 通用知识底座，需要与我们的业务对象整合 | 不是现成的公众号运营工作台，需要适配 |
| 运维与成本 | 本地桌面＋SQLite；模型和外部接口按实际使用 | 功能更完整，常规部署涉及多个服务；成本取决于部署模式、解析、嵌入与模型 | 图文件可本地保存；代码解析可不用 LLM，文档/图片语义处理仍可能消耗模型额度 |

WeKnora 已支持图相关能力，不能简单理解为“只有向量”；Graphify 也支持非代码资料，不能理解为“只能分析代码”。[WeKnora 官方说明](https://github.com/Tencent/WeKnora)，[Graphify 官方说明](https://github.com/Graphify-Labs/graphify/blob/26b02b5e3430e4ab85dd7e72c7b98836d8e65c48/README.md)。

## 我们现在真正的短板

`backend/jobs.py` 的 `contextual_ids` 在用户范围内，从已确认、未删除、允许 AI 使用且身份适配的知识中进行关键词匹配；自动追加至多 8 条，资料总量至多 20 条。`context` 每条资料读取最多 15000 字符，使用资料 ID 引用，并加入已确认身份和记忆。

这能支持小规模、明确主题的工作，但存在以下限制：

- 相同含义、不同用词可能匹配不到；长文关键内容在后半部分可能未被带入模型。
- 缺少按段落/页码定位的证据片段，用户核对成本较高。
- 有有效时间字段，不代表已经实现完整的时效推理和冲突裁决。
- 没有自己的检索质量基准，不能承诺“记住所有资料”或准确率领先。

优势是已经把“来源文章、用户观点、AI 建议、候选知识、确认知识”放在业务流程中处理，且资料留在本地。对我们的用户，这些流程仍有价值，不应为引入更强检索而丢失。

## 借鉴什么

**WeKnora：优先借鉴分块、混合检索、引用和模型职责分离。** 不要求接入其整套系统。 官方实现提供文档解析、混合检索、可替换存储和模型、接口及权限机制。适合资料量增长后的检索需求。接入时只传入用户授权的资料，返回带出处的片段，仍由梯见决定哪些知识经过确认、适用于哪个身份和时间范围。[官方 README](https://github.com/Tencent/WeKnora/blob/5574ebc0118e862ee1519d3700b8e73eb5b13c5b/README.md)、[部署配置](https://github.com/Tencent/WeKnora/blob/5574ebc0118e862ee1519d3700b8e73eb5b13c5b/docker-compose.yml)、[知识服务实现](https://github.com/Tencent/WeKnora/blob/5574ebc0118e862ee1519d3700b8e73eb5b13c5b/internal/application/service/knowledge.go)。部署配置也存在 SQLite/Lite 相关路径，不能断言任何用法都必须启用全部数据库和图组件。

**Graphify：借鉴关系来源标记与增量建图。** 可用于“企业—产品—政策—应用场景—事故案例”等关系探索，把直接提取、推断和不明确的关系区分展示。文档的语义关系仍可能有误，必须回到原文验证。官方示例的 token 节省倍数不能用来承诺我们的公众号资料成本。[官方仓库](https://github.com/Graphify-Labs/graphify)。

## 建议的升级次序（讨论稿，未实施）

1. 先保留现有确认流程，建立统一资料与片段模型：资料版本、页码/段落、来源链接、发布时间、获取时间、权限、可用状态。
2. 实现中文全文检索和分块引用；再按需求增加向量召回与重排。允许本地或外部检索后端切换，模型与嵌入费用单独标示。
3. 用真实业务问题建立评测集：同义表达、长文后段、无答案、过期政策、观点冲突、不同用户权限隔离。核对是否找到了正确证据，而非只看回答流畅度。
4. 先用我们自己的资料和问题验证上述能力。是否自建轻量实现或复用外部服务，应另行讨论；不把接入 WeKnora 或 Graphify 当作既定任务。
5. 当用户确实需要跨文档关系分析，再加入图谱；推断关系必须显示为待验证，不能自动升级成已确认事实。

以上为规划，本版没有安装 WeKnora 或 Graphify，也没有对它们开放工作区资料和模型凭据。商业集成前应复核所选版本和实际依赖许可；不能只根据 README 的开源标记判断所有组件的分发条件。
